## 7. Diagnostic

Le message de log désigne une violation de contrainte, non une erreur
applicative. Le chemin d'inscription comporte deux écritures dans `profiles` :

1. **Un trigger PostgreSQL** `handle_new_user`, déclenché par la création de
   l'utilisateur dans `auth.users`, qui insère le profil public.
2. **Un `upsert` explicite** depuis le contrôleur d'inscription, destiné à
   garantir la cohérence si le trigger échoue.

Inspection de la contrainte en base :

```sql
-- Contrainte en vigueur avant correction
CHECK (role IN ('client', 'admin', 'member', 'owner'))
```

**`'studio'` n'y figurait pas.** Les deux écritures échouaient donc pour un
compte Studio. Le trigger, avec une valeur de repli `COALESCE(…, 'client')`,
aboutissait à un profil Client ; l'`upsert` du contrôleur échouait dans un
`try/catch` qui journalisait sans interrompre le flux. L'inscription
s'achevait donc « avec succès », sur un profil au mauvais rôle.

Hypothèses écartées en chemin :

| Hypothèse | Vérification | Conclusion |
|---|---|---|
| Le front n'envoie pas le rôle | Charge utile de la requête inspectée : `role: "studio"` présent | ❌ |
| Le contrôleur normalise mal le rôle | `role === 'studio' ? 'studio' : 'client'` — correct | ❌ |
| La contrainte de base rejette `'studio'` | Définition de la contrainte inspectée | ✅ **confirmée** |

## 8. Cause racine

**Le vocabulaire des rôles a divergé entre l'application et la base.**

Le rôle `studio` a été introduit côté applicatif lors de la refonte de
l'authentification, sans migration correspondante sur la contrainte `CHECK` de
`profiles.role`, écrite à une époque où le rôle s'appelait autrement. La base
refusait donc une valeur que l'application considérait comme valide.

Deux facteurs aggravants ont transformé une erreur de données en défaut
silencieux :

- le `try/catch` du contrôleur **avalait l'erreur** sans la propager ni la
  signaler à l'appelant ;
- la valeur de repli du trigger (`COALESCE(…, 'client')`) **substituait
  silencieusement** un rôle valide à un rôle rejeté, produisant un état
  cohérent en apparence mais faux.

Une contrainte de base de données est une règle métier. Lorsqu'elle est
dupliquée dans le code applicatif, les deux copies divergent tôt ou tard — et
rien ici ne signalait la divergence.

## 9. Correctif

**Base de données** — migration [`013_fix_profiles_role_check.sql`](../../server/scripts/migrations/013_fix_profiles_role_check.sql) (commits `d20e4d3`, `be52bf5`)

```sql
-- 1. Aligner la contrainte sur le vocabulaire applicatif
ALTER TABLE public.profiles DROP CONSTRAINT IF EXISTS profiles_role_check;
ALTER TABLE public.profiles ADD CONSTRAINT profiles_role_check
  CHECK (role IN ('studio', 'client', 'admin', 'member', 'owner'));

-- 2. Rendre le trigger idempotent et complet
CREATE OR REPLACE FUNCTION public.handle_new_user()
RETURNS trigger AS $$
BEGIN
  INSERT INTO public.profiles (id, name, email, role, siret)
  VALUES (
    new.id,
    COALESCE(new.raw_user_meta_data->>'name', split_part(new.email, '@', 1)),
    new.email,
    COALESCE(new.raw_user_meta_data->>'role', 'client'),
    new.raw_user_meta_data->>'siret'
  )
  ON CONFLICT (id) DO UPDATE SET
    email = EXCLUDED.email,
    name  = COALESCE(EXCLUDED.name, profiles.name),
    role  = COALESCE(EXCLUDED.role, profiles.role);
  RETURN new;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;
```

**API** — commit [`faa9a27`](https://github.com/flavienderoy/myvisuals-back/commit/faa9a27)

L'erreur d'`upsert` cesse d'être avalée : elle est explicitement récupérée et
journalisée avec son message.

```diff
- } catch (profErr) {
-   console.error('Error upserting profile in register:', profErr);
+ const { error: profErr } = await supabase.from('profiles').upsert({ … });
+
+ if (profErr) {
+   console.error('Profile upsert failed during register:', profErr.message);
+   // Non bloquant : l'utilisateur existe déjà côté auth, le profil est réparable
  }
```

Le nom et les champs facultatifs sont par ailleurs normalisés
(`name.trim()`, `siret: siret || null`), le nom devient obligatoire, et le
message d'erreur de robustesse du mot de passe précise désormais **quel**
critère manque plutôt que de les énumérer tous.

**Front** — commits `7798ec2`, `93ca8df`, `e347c50` : charge utile d'inscription
explicite, résolution du rôle fiabilisée à la connexion, et connexion
automatique après inscription afin qu'une session antérieure ne prenne pas le
pas sur la nouvelle.

## 10. Test de non-régression

Six cas ajoutés dans
[`__tests__/authRegistration.test.js`](../../server/__tests__/authRegistration.test.js) :

| Cas | Ce qu'il verrouille |
|---|---|
| Le rôle `studio` demandé est écrit dans `profiles` | Le défaut lui-même |
| Le rôle `studio` est propagé aux métadonnées du compte | Le trigger lit ces métadonnées : sans elles, repli sur `client` |
| Le rôle `client` demandé est bien écrit | Non-régression du cas nominal |
| Un rôle inconnu (`admin`) est ramené à `client` | Aucune élévation de privilège depuis la charge utile |
| Nom normalisé, champs facultatifs absents → `null` | Correctifs annexes du même commit |
| Un rejet d'écriture du profil est journalisé explicitement | Le silence qui avait masqué l'anomalie |

### Vérification par mutation

Un test qui passe ne prouve rien tant qu'on n'a pas vérifié qu'il peut échouer.
Le correctif a donc été retiré temporairement, en deux mutations distinctes :

| Mutation appliquée | Résultat |
|---|---|
| `const userRole = 'client'` — rôle systématiquement ramené à `client` | **2 tests en échec** (écriture du profil, métadonnées) |
| Suppression du `console.error` sur `profErr` — rejet à nouveau avalé | **3 tests en échec** (les deux précédents + journalisation) |

Le contrôleur a ensuite été restauré depuis git, et la suite complète repasse
au vert (90 tests).

**Lacune assumée** : la contrainte `CHECK` elle-même n'est pas couverte — les
tests s'exécutent contre un client Supabase simulé, non contre une base réelle.
C'est précisément la frontière où le défaut est né. Un test d'intégration sur
une instance PostgreSQL éphémère serait nécessaire pour détecter cette classe
de dérive ; porté en recommandation d'amélioration.

## 11. Action préventive

| Mesure | Effet |
|---|---|
| Les erreurs d'écriture de profil ne sont plus avalées | Un rejet de contrainte devient visible dans les logs et remonte à Sentry |
| Trigger idempotent (`ON CONFLICT DO UPDATE`) | Le trigger et l'`upsert` du contrôleur ne se contredisent plus |
| Migration numérotée et versionnée | Toute évolution du vocabulaire des rôles passe désormais par une migration tracée |

Reste à traiter : les rôles sont définis à trois endroits (contrainte SQL,
contrôleur, front). Centraliser cette énumération est porté en recommandation.

## 13. Analyse post-incident

| Question | Réponse |
|---|---|
| **Pourquoi le défaut a-t-il été introduit ?** | Le rôle `studio` a été ajouté côté applicatif sans migration de la contrainte `CHECK` correspondante. Le vocabulaire des rôles est dupliqué entre la base, l'API et le front, sans source unique de vérité. |
| **Pourquoi n'a-t-il pas été détecté plus tôt ?** | Deux mécanismes de repli ont masqué l'erreur : un `try/catch` qui journalisait sans propager, et un `COALESCE` du trigger substituant silencieusement `client`. L'inscription se terminait « avec succès ». Les tests s'exécutant contre un client Supabase simulé, la contrainte réelle n'était jamais éprouvée. |
| **Qu'est-ce qui empêchera sa récidive ?** | Les erreurs d'écriture de profil sont désormais explicitement récupérées et remontées à la sonde applicative ; les évolutions du vocabulaire des rôles passent par une migration numérotée. Un test d'intégration sur base réelle reste à mettre en place. |

### Enseignements retenus

**Un mécanisme de repli qui masque une erreur est pire que l'erreur.** Le
`COALESCE` et le `try/catch` avaient été écrits pour rendre l'inscription
robuste. Ils ont produit l'inverse : un état incohérent, silencieux, découvert
par un utilisateur plutôt que par la supervision. Un repli n'est acceptable que
s'il **signale** ce qu'il a compensé.

**Le canal de détection est un indicateur en soi.** Cette anomalie a été
découverte par un utilisateur, sur le tout premier écran du produit. Elle
figure dans le décompte de l'indicateur *part des anomalies détectées avant
signalement client* ([SUPERVISION.md § 4](../SUPERVISION.md#4-indicateurs-de-suivi))
du mauvais côté — et c'est précisément ce que cet indicateur doit rendre
visible.
