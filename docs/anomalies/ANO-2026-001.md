## 1. Description

À la suite d'un déploiement sur Cloud Run, le service `visuals-api` ne démarre
plus. Le conteneur s'arrête immédiatement après son lancement et Cloud Run le
relance en boucle. **Aucune route de l'API n'est joignable** : l'application
front reste affichée mais toutes les requêtes échouent.

Le point notable est que **l'ensemble de la chaîne d'intégration continue était
verte** : lint, tests unitaires et d'intégration, et construction de l'image
Docker ont tous réussi avant le déploiement.

## 2. Comportement attendu / observé

| Attendu | Observé |
|---|---|
| Le conteneur démarre, `/health` répond `200 OK` | Le conteneur s'arrête au démarrage, redémarrages en boucle |
| L'API sert les routes `/api/**` | Toutes les requêtes échouent (503 côté Cloud Run) |
| Un build Docker réussi implique une image exécutable | Le build réussit, l'image ne démarre pas |

## 3. Étapes de reproduction

1. Se placer sur le commit précédant `a942974`.
2. Construire l'image : `docker build -t visuals-api:repro ./server`
   → **le build réussit**.
3. Démarrer le conteneur : `docker run -p 8080:8080 visuals-api:repro`
4. Observer l'arrêt immédiat du process et la trace ci-dessous.

Reproduction déterministe : le défaut se manifeste à chaque exécution.

## 4. Preuves

| Question | Réponse |

## 6. Diagnostic

La trace désigne sans ambiguïté un module absent du système de fichiers de
l'image, et non une erreur applicative. Trois hypothèses ont été examinées :

| Hypothèse | Vérification | Conclusion |
|---|---|---|
| Dépendance npm manquante | `utils/pagination` est un module **local**, pas un paquet npm | ❌ écartée |
| Fichier absent du dépôt | `git ls-files server/utils/` liste bien `pagination.js` | ❌ écartée |
| Fichier absent de **l'image Docker** | `docker run --rm visuals-api:repro ls /app` → pas de dossier `utils/` | ✅ **confirmée** |

Le dossier existe dans le dépôt mais pas dans l'image : le défaut est dans les
instructions de construction, pas dans le code applicatif.

## 7. Cause racine

Le `Dockerfile` de production copiait les sources **dossier par dossier**, par
énumération explicite :

```dockerfile
COPY config/ ./config/
COPY controllers/ ./controllers/
COPY middlewares/ ./middlewares/
COPY routes/ ./routes/
COPY scripts/ ./scripts/
```

Cette liste avait été écrite à un moment où `utils/` n'existait pas encore. Le
dossier a été introduit ensuite (pagination, traitement d'images, journal
d'activité — utilisé par plus de dix contrôleurs), ainsi que
`swaggerOptions.js`, sans que la liste ne soit mise à jour. **Toute énumération
manuelle de fichiers dérive à mesure que le projet grandit** ; rien, dans la
chaîne, ne signalait cette dérive.

Le second facteur, plus important que le premier : **`docker build` n'exécute
jamais l'application**. Il empile des couches de système de fichiers. Une image
à laquelle il manque un fichier requis au démarrage se construit donc sans la
moindre erreur. Le job `docker` de la CI vérifiait que l'image *se construit*,
ce qui ne dit rien de sa capacité à *démarrer*. Le premier moment de vérité
était le déploiement en production — c'est-à-dire trop tard.

## 8. Correctif

Commit [`a942974`](https://github.com/flavienderoy/myvisuals-back/commit/a942974) — *fix(docker): copy utils/ and swaggerOptions.js into the runtime image*

```diff
  COPY app.js ./
  COPY server.js ./
+ COPY swaggerOptions.js ./
  COPY config/ ./config/
  COPY controllers/ ./controllers/
  COPY middlewares/ ./middlewares/
  COPY routes/ ./routes/
+ COPY utils/ ./utils/
  COPY scripts/ ./scripts/
```

Correctif volontairement minimal : rétablir le contenu de l'image, sans
refonte du `Dockerfile` dans le même changement. Une restructuration de la
stratégie de copie aurait rendu le retour arrière plus risqué au moment
précis où la production était à l'arrêt.

## 9. Test de non-régression

Un test unitaire ne peut rien contre cette classe de défaut : les tests
s'exécutent sur l'arborescence du dépôt, où `utils/` est bien présent. **Le
défaut n'existe que dans l'artefact déployé.** Le test de non-régression devait
donc porter sur l'image elle-même — d'où l'action préventive ci-dessous, qui
tient ici lieu de test.

## 10. Action préventive

Un *smoke test* a été ajouté au job `docker` de la CI. Il ne se contente plus de
construire l'image : il **démarre réellement le conteneur** et interroge
`/health` ([`.github/workflows/ci.yml`](../../.github/workflows/ci.yml)).

```yaml
- name: Smoke test — boot container & check /health
  run: |
    docker run -d --name visuals-api-smoke -p 8080:8080 \
      -e NODE_ENV=production \
      -e SUPABASE_URL=https://placeholder.supabase.co \
      -e SUPABASE_SERVICE_ROLE_KEY=placeholder \
      visuals-api:ci
    for i in $(seq 1 15); do
      if curl -fsS http://localhost:8080/health >/dev/null 2>&1; then
        echo "✅ /health responded — container boots correctly"
        docker rm -f visuals-api-smoke >/dev/null
        exit 0
      fi
      sleep 2
    done
    echo "❌ Container failed to serve /health within 30s — dumping logs:"
    docker logs visuals-api-smoke || true
    docker rm -f visuals-api-smoke >/dev/null
    exit 1
```

Portée de cette mesure : elle ne corrige pas un fichier oublié, elle rend
**structurellement impossible** le déploiement d'une image qui ne démarre pas —
quelle qu'en soit la raison (fichier manquant, erreur de syntaxe au chargement,
variable d'environnement obligatoire absente, version de Node incompatible).
Une classe entière de défauts est déplacée de la production vers la CI.

C'est aussi ce qui a motivé la sonde `/health/ready`
([SUPERVISION.md § 3.2](../SUPERVISION.md)) : le smoke test valide que le process
démarre, la sonde d'aptitude valide qu'il peut réellement servir.

## 11. Vérification

1. CI relancée sur le correctif : le job `docker`, smoke test inclus, passe au vert.
2. Déploiement automatique sur Cloud Run.
3. `curl https://<api>/health` → `200 OK`.
4. Vérification du contenu de l'image :
   `docker run --rm visuals-api:ci ls /app` → `utils/` présent.

### Contre-épreuve du mécanisme

Montrer qu'un garde-fou laisse passer une image saine ne prouve rien : encore
faut-il vérifier qu'il **rejette** une image défectueuse. Le mécanisme de
défaillance a donc été rejoué en reconstituant l'arborescence exacte que
produisaient les `COPY` fautifs — toutes les sources **sauf** `utils/` et
`swaggerOptions.js` :

```console
$ cp package.json app.js server.js "$REPRO"/
$ cp -r config controllers middlewares routes scripts node_modules "$REPRO"/   # utils/ volontairement omis
$ cd "$REPRO" && NODE_ENV=production node server.js

Error: Cannot find module '../utils/logger'
Require stack:
- /…/repro-ano001/config/monitoring.js
- /…/repro-ano001/app.js
- /…/repro-ano001/server.js
    at Module._resolveFilename (node:internal/modules/cjs/loader:1420:15)
  code: 'MODULE_NOT_FOUND'
```

Le process s'arrête au chargement, avant toute écoute sur le port : `/health`
ne peut donc structurellement pas répondre, et le smoke test échoue. Le module
cité diffère de celui de l'incident d'origine (`utils/logger` au lieu de
`utils/pagination`) simplement parce que l'arborescence actuelle charge
`config/monitoring.js` plus tôt — la classe de défaillance et son effet sont
identiques.

> **Contre-épreuve complète sur l'image Docker** — à exécuter avec un démon
> Docker actif, pour reproduire la chaîne de bout en bout :
> ```bash
> git stash && git checkout a942974~1 -- server/Dockerfile
> docker build -t visuals-api:defect ./server
> docker run -d --name smoke-defect -p 8080:8080 visuals-api:defect
> curl -fsS http://localhost:8080/health   # doit échouer
> docker logs smoke-defect                 # doit afficher MODULE_NOT_FOUND
> docker rm -f smoke-defect && git checkout HEAD -- server/Dockerfile && git stash pop
> ```

## 12. Analyse post-incident

| Question | Réponse |
|---|---|
| **Pourquoi le défaut a-t-il été introduit ?** | Le `Dockerfile` énumérait les dossiers à copier un par un. Cette liste est un doublon de l'arborescence du projet, qu'aucun mécanisme ne tenait à jour : l'ajout de `utils/` n'a pas été répercuté. |
| **Pourquoi n'a-t-il pas été détecté plus tôt ?** | La CI vérifiait que l'image *se construit*, jamais qu'elle *démarre*. `docker build` n'exécute pas l'application : un fichier manquant au moment de l'exécution est invisible à la construction. Les tests, eux, s'exécutent sur le dépôt et non sur l'image. |
| **Qu'est-ce qui empêchera sa récidive ?** | Le smoke test qui démarre le conteneur et interroge `/health` à chaque exécution de la CI. Toute image non démarrable échoue désormais avant le déploiement. |

### Enseignement retenu

**Un artefact doit être testé sous la forme exacte dans laquelle il sera
déployé.** Tester le code source ne dit rien de l'image ; construire l'image ne
dit rien de son exécution. C'est précisément à ces frontières — entre le dépôt
et l'image, entre l'image et le service — que se logent les défauts les plus
coûteux, parce qu'ils échappent aux tests situés de part et d'autre.

### Amélioration identifiée, non retenue à ce stade

Remplacer l'énumération par `COPY . ./` accompagné d'un `.dockerignore`
exhaustif supprimerait la cause première (la liste manuelle). Cette
modification n'a pas été appliquée dans le correctif d'urgence, pour ne pas
élargir la surface de changement pendant une indisponibilité. Elle est portée
en recommandation d'amélioration : le smoke test couvrant désormais le
symptôme, le risque résiduel est faible et l'arbitrage peut être fait à froid.
