## 1. Description

Toutes les requêtes du front vers l'API sont rejetées par le navigateur :

```
Access to XMLHttpRequest at 'https://myvisuals-back-…run.app/api/projects'
from origin 'https://myvisuals-client.vercel.app' has been blocked by CORS policy:
Response to preflight request doesn't pass access control check:
No 'Access-Control-Allow-Origin' header is present on the requested resource.
```

L'application se charge, l'authentification fonctionne, mais **aucune donnée métier n'est accessible** : projets, clients, tâches, notifications — tout échoue simultanément.

## 2. Comportement attendu / observé

| Attendu | Observé |
|---|---|
| Le préflight renvoie `Access-Control-Allow-Origin` | 204 **sans** l'en-tête |
| Le tableau de bord charge les données | `AxiosError: Network Error` sur 10 appels |
| Une panne de cette ampleur déclenche une alerte | **Aucune alerte** — tous les indicateurs au vert |

## 3. Preuves

```console
$ gcloud run services describe myvisuals-back --format="...env"
{'name': 'CLIENT_URL', 'value': 'https://myvisuals-client.vercel.app/'}
                                                                   ↑ slash terminal

$ curl -X OPTIONS -H "Origin: https://myvisuals-client.vercel.app" …/api/projects -D -
HTTP/2 204
vary: Origin, Access-Control-Request-Headers
access-control-allow-credentials: true
access-control-allow-methods: GET,HEAD,PUT,PATCH,POST,DELETE
→ aucun access-control-allow-origin
```

## 4. Impact

| Question | Réponse |
|---|---|
| Utilisateurs touchés | **Tous** — studios et clients |
| Fonctions concernées | Toutes les fonctions métier ; seule l'authentification survivait (elle passe par Supabase en direct) |
| Depuis quand | ≈ 2 jours, du 2026-08-15 14 h 51 au 2026-08-17 19 h 57 |
| Contournement | Aucun |

## 5. Cause racine

**Une barre oblique finale.**

L'en-tête `Origin` d'un navigateur ne porte **jamais** de slash terminal (RFC 6454 : il se limite au schéma, à l'hôte et au port). La variable `CLIENT_URL` valait `https://myvisuals-client.vercel.app/`. Le module `cors` effectuait une comparaison de chaînes exacte contre la liste d'origines : aucune correspondance, donc aucun en-tête émis.

**Comment la valeur fautive est arrivée là.** Le service `myvisuals-back` avait été configuré manuellement, avec une valeur correcte. Le correctif d'[ANO-2026-004](./ANO-2026-004.md) a fait passer le déploiement par `--set-env-vars "…CLIENT_URL=${{ secrets.CLIENT_URL }}…"`. Or le secret GitHub contenait le slash. **Le premier déploiement automatisé a écrasé la bonne valeur par la mauvaise.**

C'est une régression introduite par un correctif — et par un correctif dont l'objet était précisément de fiabiliser les déploiements.

## 6. Pourquoi rien ne l'a détectée

C'est le point le plus instructif de cette anomalie. **Côté serveur, tout était sain** :

| Sonde | Verdict | Pourquoi elle ne voit rien |
|---|---|---|
| `/health` | `ok` | Le process répond |
| `/health/ready` | `ok` | Base et stockage joignables |
| Vérification post-déploiement en CI | ✅ | Interroge l'API sans en-tête `Origin` |
| Taux de 5xx | normal | Le préflight renvoie 204, pas une erreur |
| Sentry backend | silencieux | Aucune exception levée |
| Uptime check | vert | `/health/ready` répond 200 |

**La panne n'existait que dans le navigateur.** Une politique CORS mal configurée n'est pas une erreur serveur : c'est une réponse correcte, à laquelle il manque un en-tête. Le serveur fait exactement ce qu'on lui a demandé.

Aucune sonde synthétique ne peut détecter cela, parce qu'aucune ne se comporte comme un navigateur soumis à la politique de même origine.

## 7. Correctif

**Trois niveaux, du plus urgent au plus durable.**

**a. Rétablissement immédiat** — correction de la variable sur Cloud Run, service rétabli en moins d'une minute sans reconstruction.

**b. Cause amont** — correction du secret GitHub `CLIENT_URL`, sans quoi le déploiement suivant aurait réintroduit le défaut.

**c. Robustesse** — normalisation des deux côtés de la comparaison, dans [`app.js`](../../server/app.js) :

```js
const normalizeOrigin = (value) => (value || '').trim().replace(/\/+$/, '').toLowerCase();

const ALLOWED_ORIGINS = [process.env.CLIENT_URL, 'http://localhost:5173', …]
    .filter(Boolean).map(normalizeOrigin);

app.use(cors({
    origin(origin, callback) {
        if (!origin) return callback(null, true);
        if (ALLOWED_ORIGINS.includes(normalizeOrigin(origin))) return callback(null, true);
        logger.warn('cors.origin_rejected', { origin, allowed: ALLOWED_ORIGINS });
        return callback(null, false);
    },
    credentials: true,
}));
```

Corriger uniquement la variable aurait traité le symptôme. **Une erreur de saisie dans une variable d'environnement ne doit pas pouvoir rendre l'API inutilisable.**

**d. Supervision** — toute origine rejetée est désormais journalisée en `WARNING`. Un rejet CORS est soit une tentative d'accès illégitime, soit une erreur de configuration ; sans trace, les deux sont indiscernables et parfaitement silencieux.

## 8. Test de non-régression

Six cas dans [`__tests__/cors.test.js`](../../server/__tests__/cors.test.js). Le test pose délibérément `CLIENT_URL` **avec le slash fautif** — le cas exact qui a cassé la production.

Vérifié par mutation : la normalisation retirée, **2 tests sur 6 échouent**.

## 9. Vérification

```console
$ curl -sI -H "Origin: https://myvisuals-client.vercel.app" …/health | grep access-control-allow-origin
access-control-allow-origin: https://myvisuals-client.vercel.app     ✅

$ curl -sI -H "Origin: https://attaquant.example" …/health | grep access-control-allow-origin
(aucun en-tête)                                                       ✅ rejet correct
```

Révision `myvisuals-back-00012-mkk`. Tableau de bord fonctionnel, confirmé côté utilisateur.

## 10. Analyse post-incident

| Question | Réponse |
|---|---|
| **Pourquoi le défaut a-t-il été introduit ?** | Un correctif a fait passer une configuration jusque-là manuelle sous contrôle automatisé, sans vérifier que la source de vérité (le secret) contenait une valeur valide. Automatiser une configuration ne la valide pas : cela ne fait que déplacer l'endroit où l'erreur est saisie. |
| **Pourquoi n'a-t-il pas été détecté plus tôt ?** | Aucune sonde ne se comporte comme un navigateur. La supervision mesure la santé du serveur, pas l'expérience réelle de l'utilisateur. Une réponse HTTP parfaitement valide peut rendre l'application inutilisable. |
| **Qu'est-ce qui empêchera sa récidive ?** | La normalisation rend la classe de défaut impossible ; les 6 tests la verrouillent ; le journal des rejets CORS la rendrait visible. Reste la lacune de fond, traitée par la recommandation **R2**. |

### Enseignement retenu

**Une sonde technique ne mesure pas l'expérience de l'utilisateur.** ANO-2026-001 enseignait qu'un artefact doit être testé sous sa forme déployée ; ANO-2026-004, qu'un déploiement réussi n'est pas un service fonctionnel. Celle-ci ajoute le dernier maillon : **un service fonctionnel n'est pas une application utilisable.**

Les trois sont la même erreur à trois altitudes — vérifier ce qui est commode à mesurer plutôt que ce qui compte réellement.

### Ce qu'elle démontre pour le dispositif

Cette anomalie est la **justification empirique de la recommandation R2** (test de parcours réel exécuté périodiquement contre la production). Un simple scénario Playwright — se connecter, charger le tableau de bord, vérifier qu'un projet s'affiche — l'aurait détectée en moins de 15 minutes au lieu de 2 jours.

Elle ajoute également un **cinquième canal de détection** au § 3.2 du processus, le moins souhaitable de tous : *constat fortuit*. Aucun dispositif ne l'a vue ; elle a été trouvée en ouvrant l'application.
