## 1. Description

Au chargement du tableau de bord Studio, une partie des données ne s'affiche
pas : projets manquants, compteurs à zéro, listes vides. Le rechargement de la
page corrige parfois le problème, parfois non — un comportement intermittent
qui a d'abord fait suspecter un défaut de récupération de données.

Le tableau de bord déclenche environ **douze appels API en parallèle** à son
montage (projets, clients, tâches, notifications, activités, conversations…).
Une partie de ces appels reçoit un `429 Too Many Requests`.

## 2. Comportement attendu / observé

| Attendu | Observé |
|---|---|
| Les douze appels de chargement aboutissent | Une partie répond `429 Too Many Requests` |
| Le tableau de bord affiche des données complètes | Sections vides, compteurs à zéro, sans message d'erreur |
| Un dépassement de quota est signalé à l'utilisateur | Échec silencieux : l'interface paraît simplement vide |

## 3. Étapes de reproduction

1. Démarrer l'API et le front en local (`npm run dev` de part et d'autre).
2. Se connecter avec un compte Studio disposant de plusieurs projets.
3. Recharger le tableau de bord plusieurs fois d'affilée.
4. Onglet *Réseau* : plusieurs requêtes `/api/**` répondent `429`.

Le mode strict de React monte chaque composant deux fois en développement, et
le rechargement à chaud réinitialise l'état sans réinitialiser le compteur du
limiteur — ce qui accélère nettement l'atteinte du seuil.

## 4. Preuves

```
GET /api/projects        429 Too Many Requests
GET /api/notifications   429 Too Many Requests
GET /api/activities      429 Too Many Requests

{"error":"Too many requests, please try again later."}
```

Configuration en cause au moment de l'incident :

```js
const apiLimiter = rateLimit({
    windowMs: 15 * 60 * 1000,
    max: process.env.NODE_ENV === 'development' ? 5000 : 500,
});
```

## 5. Impact

| Question | Réponse |
|---|---|
| Utilisateurs touchés | Développement : systématique. Production : studios actifs (plusieurs projets, sessions longues) |
| Rôles concernés | Studio principalement — le tableau de bord Studio est le plus consommateur d'appels |
| Depuis quand | Depuis l'enrichissement du tableau de bord en 1.3.0 |
| Contournement | Attendre la fin de la fenêtre de 15 minutes, ou recharger la page |

## 6. Diagnostic

L'hypothèse initiale — un défaut de récupération de données — a été écartée
dès l'inspection de l'onglet *Réseau* : les requêtes partaient bien et
recevaient une réponse, mais un `429`. Le défaut n'était pas dans le
chargement, mais dans son volume.

Deux facteurs se combinent :

1. **Volume par session.** Le seuil de 500 requêtes par tranche de 15 minutes
   avait été fixé lorsque l'application comptait peu d'écrans. Le tableau de
   bord consomme désormais ~12 appels à chaque montage ; quelques navigations
   entre projets suffisent à s'en approcher en production.
2. **Absence de tolérance côté client.** Un `429` est une réponse *temporaire*,
   assortie d'un en-tête `RateLimit-Reset`. La couche HTTP du front la traitait
   comme un échec définitif : la promesse était rejetée, la section restait
   vide, et aucun message n'était présenté à l'utilisateur.

Le second point est le plus important. Même correctement dimensionné, un
limiteur finira par se déclencher un jour — sur un pic d'usage, une reprise
après incident ou un utilisateur particulièrement actif. Une application qui ne
sait pas absorber un `429` reste fragile quel que soit le seuil retenu.

## 7. Cause racine

**Deux causes distinctes, l'une de dimensionnement, l'autre de conception.**

- *Dimensionnement* : un seuil calibré sur une version antérieure de
  l'application, jamais réévalué à mesure que le tableau de bord s'enrichissait.
- *Conception* : aucune stratégie de reprise côté client face à une réponse
  explicitement temporaire.

Corriger uniquement le seuil aurait repoussé le problème sans le traiter.

## 8. Correctif

**API** — commit [`2497a8f`](https://github.com/flavienderoy/myvisuals-back/commit/2497a8f)

```diff
- max: process.env.NODE_ENV === 'development' ? 5000 : 500,
+ const isDev = process.env.NODE_ENV === 'development' || !process.env.NODE_ENV;
+ max: isDev ? 10000 : 1000,   // le tableau de bord déclenche ~12 appels par montage
+ skip: isDev ? (req) => {
+     // Jamais de limitation sur localhost en développement
+     const ip = req.ip || req.connection?.remoteAddress || '';
+     return ip === '127.0.0.1' || ip === '::1' || ip === '::ffff:127.0.0.1';
+ } : undefined,
```

Le seuil de production est doublé (500 → 1000) : il protège toujours contre le
bourrinage d'authentification, sans pénaliser un usage normal. La limitation
est neutralisée sur `localhost` **en développement uniquement** — la condition
`isDev` garantit que la production reste protégée.

**Front** — commit [`418a42f`](https://github.com/flavienderoy/myvisuals-client/commit/418a42f), [`src/services/api.js`](../../client/src/services/api.js)

```js
// Réessai automatique des 429 avec temporisation exponentielle
if (error.response?.status === 429 && config && config.__retryCount < 3) {
    config.__retryCount += 1;
    const delay = Math.pow(2, config.__retryCount - 1) * 1000; // 1s, 2s, 4s
    await new Promise((r) => setTimeout(r, delay));
    return api(config);
}
```

La temporisation est **exponentielle** et non fixe : réessayer immédiatement,
ou à intervalle constant, ajoute de la charge à un service qui signale déjà sa
saturation. Le nombre de tentatives est borné à trois pour éviter qu'un service
durablement indisponible ne provoque des réessais sans fin.

Le même changement dédoublonne les appels concurrents à `loadCoreData` dans le
contexte de données, ce qui réduit le volume à la source.

## 9. Test de non-régression

Couverture existante, dans [`__tests__/security.test.js`](../../server/__tests__/security.test.js) :
le limiteur est actif sur `/api/**` et renvoie les en-têtes `RateLimit-*`
normalisés.

**Lacune assumée** : la temporisation exponentielle côté front n'est pas
couverte par un test automatisé. C'est la faiblesse principale de ce correctif
et elle est portée en recommandation d'amélioration — un test simulant trois
`429` consécutifs et vérifiant les délais 1 s / 2 s / 4 s avec des minuteurs
simulés.

## 10. Action préventive

Un indicateur de supervision dédié a été créé à la suite de cette anomalie
(indicateur 7, [SUPERVISION.md § 4](../SUPERVISION.md#4-indicateurs-de-suivi)) :

| Indicateur | Sonde | Seuil | Sévérité |
|---|---|---|---|
| Saturation du limiteur de débit | Log-based metric `statusCode=429` | > 50 / h | S3 |

Un `429` n'est pas un incident en soi — c'est un mécanisme de protection qui
fonctionne. Mais un *volume* de `429` signale soit un usage anormal, soit un
dimensionnement à revoir. Sans cet indicateur, la saturation en production
serait restée invisible : le réessai automatique la masque désormais aux yeux
de l'utilisateur, ce qui la rend d'autant plus nécessaire à surveiller côté
exploitation.

Cet effet de bord est à souligner : **un correctif qui rend une anomalie
invisible sans la supprimer crée une dette de supervision.** L'indicateur est
la contrepartie du réessai.

## 11. Vérification

1. Rechargements répétés du tableau de bord en local : plus aucun `429`.
2. Vérification que la production reste protégée : `NODE_ENV=production` avec
   des appels au-delà du seuil → `429` correctement renvoyé.
3. Onglet *Réseau* : une requête `429` isolée est bien rejouée après 1 s et
   aboutit, sans manifestation visible côté utilisateur.

## 12. Analyse post-incident

| Question | Réponse |
|---|---|
| **Pourquoi le défaut a-t-il été introduit ?** | Le seuil du limiteur avait été fixé pour une version plus légère de l'application et n'a pas été réévalué à mesure que le tableau de bord s'enrichissait. Aucune revue périodique ne portait sur ce paramètre. |
| **Pourquoi n'a-t-il pas été détecté plus tôt ?** | Un `429` était traité côté front comme un échec silencieux : l'interface affichait des sections vides sans message d'erreur. Le symptôme ressemblait à une absence de données, pas à un rejet du serveur. |
| **Qu'est-ce qui empêchera sa récidive ?** | Le réessai avec temporisation exponentielle absorbe les dépassements ponctuels ; l'indicateur de supervision sur le volume de `429` rend visible une saturation durable avant qu'elle n'affecte les utilisateurs. |

### Enseignement retenu

**Un échec silencieux coûte plus cher qu'une erreur affichée.** Le temps de
diagnostic a été consacré pour l'essentiel à comprendre *que* les requêtes
échouaient — l'interface, en présentant des sections vides, décrivait un état
qui n'existait pas. Une réponse d'erreur non traitée par le client n'est pas
neutre : elle produit une information fausse.
