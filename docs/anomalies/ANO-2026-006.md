## 1. Description

Après une remise à zéro des données de test, plusieurs comptes (un studio, un client) se sont connectés à la suite. Dès lors, des actions pourtant autorisées échouent pour le studio comme pour le client : création d'entreprise refusée, commentaires impossibles à valider, messages impossibles à envoyer.

## 2. Comportement attendu / observé

| Action | Attendu | Observé |
|---|---|---|
| Le studio crée une entreprise | 201 | 500 `new row violates row-level security policy for table "clients"` |
| Le studio valide le commentaire d'un client | 200 | 404 `Annotation not found or not a root ticket` |
| Le client envoie un message dans le canal du projet | 201 | 500 |
| Le résultat dépend de l'auteur de la requête | Oui | **Non** : il dépend du **dernier compte connecté** sur l'instance |

## 3. Étapes de reproduction

1. Se connecter avec un compte studio A.
2. Se connecter (depuis un autre navigateur) avec un compte client B.
3. Avec le compte A, créer une entreprise : refus RLS, car la requête part avec le jeton de B.

Reproduction minimale, sans navigateur : créer un compte, appeler `POST /api/auth/login`, puis lire le jeton que le client partagé envoie à la base (§ 4).

## 4. Preuves

Journaux Cloud Run (extraits), deux comptes connectés à 11 h 55 et 11 h 56 :

## 5. Impact

| Question | Réponse |
|---|---|
| Utilisateurs touchés | Tous, dès que deux comptes se connectent sur la même instance Cloud Run |
| Rôles concernés | Studio, client et membres d'équipe |
| Depuis quand | Le commit initial. Invisible tant qu'un seul compte se connectait : sa propre session correspondait aux données qu'il manipulait |
| Contournement | Se reconnecter juste avant l'action, ce qui redonne la main à son propre compte jusqu'à la connexion suivante d'un autre utilisateur. Non viable |

**Confidentialité.** Les contrôleurs filtrent par l'identifiant de l'auteur réel (`req.user.id`), ce qui limite une lecture croisée. Mais toute requête était soumise aux politiques RLS d'un tiers : l'API ne garantissait plus que chaque utilisateur agit avec ses propres droits. D'où la classification S1.

## 6. Diagnostic

1. **Hypothèse écartée : données corrompues après la remise à zéro.** La même insertion, rejouée avec la clé `service_role` depuis un script local, réussit.
2. **Hypothèse écartée : code déployé différent du dépôt.** La révision en production correspond au dernier commit ; le contrôleur n'avait pas changé.
3. **Hypothèse écartée : taille ou contenu de la requête.** Trois tentatives avec des noms différents renvoient un corps d'erreur de taille identique : un message fixe.
4. **Le message RLS est incompatible avec la clé `service_role`**, qui contourne RLS. La requête partait donc avec un autre jeton.
5. **Lecture de supabase-js 2.98** : `SupabaseClient._getAccessToken()` renvoie le jeton de la session courante s'il existe, sinon la clé du client. Or `authController.login` appelait `signInWithPassword` sur le client partagé.
6. **Lecture d'auth-js** : même avec `persistSession: false`, la session est rangée dans un stockage mémoire et reste lue par `getSession()`. Désactiver la persistance ne suffit donc pas.

## 7. Cause racine

Un **client unique, à privilèges élevés, partagé par toutes les requêtes** a été utilisé pour une opération **qui ouvre une session utilisateur**. Le SDK est conçu pour un navigateur, où « client » et « utilisateur » ne font qu'un ; côté serveur, cet état implicite devient un état global partagé entre tous les utilisateurs.

## 8. Correctif

**Commit** : `fix(auth): isoler la session de connexion du client Supabase partagé`

```diff
 // config/supabase.js
-const supabase = createClient(supabaseUrl || '…', supabaseServiceKey || '…');
+const createServerClient = () => createClient(
+    supabaseUrl || '…',
+    supabaseServiceKey || '…',
+    { auth: { persistSession: false, autoRefreshToken: false, detectSessionInUrl: false } },
+);
+const supabase = createServerClient();
 module.exports = supabase;
+module.exports.createServerClient = createServerClient;

 // controllers/authController.js — login
-const { data, error } = await supabase.auth.signInWithPassword({ email, password });
+const { data, error } = await supabase.createServerClient().auth.signInWithPassword({ email, password });
```

Le client jetable n'existe que le temps de la requête de connexion ; la session qu'il contient est renvoyée au front puis abandonnée.

## 9. Test de non-régression

`server/__tests__/authSession.test.js` :

- la connexion passe par un client créé pour l'occasion, et `signInWithPassword` n'est **jamais** appelé sur le client partagé ;
- `createServerClient()` renvoie un client distinct à chaque appel.

**Vérifié par mutation** : l'ancien `authController.js` restauré, le premier test échoue (`expected 401 to be 200`, l'appel part sur le client partagé). Suite complète : 98 tests au vert.

## 10. Action préventive

- **Le client partagé ne peut plus porter de session** : persistance et rafraîchissement désactivés, et toute opération qui ouvre une session passe par `createServerClient()`.
- **Test qui échoue si la connexion revient sur le client partagé**, exécuté par la CI à chaque push.
- Point de vigilance consigné ici pour toute évolution future : `signInWithPassword`, `signUp`, `verifyOtp`, `exchangeCodeForSession`, `setSession` et `refreshSession` ne doivent jamais être appelés sur le client exporté par `config/supabase.js`.

## 11. Vérification

- Preuve locale sur le projet Supabase réel, avant et après correctif (§ 4).
- **En production, à la publication de 1.6.4** : connecter successivement un studio puis un client, puis avec le studio créer une entreprise et valider un commentaire, et avec le client envoyer un message. Attendu : 201, 200 et 201.

## 12. Analyse post-incident

| Question | Réponse |
|---|---|
| Pourquoi le défaut a-t-il été introduit ? | Le SDK Supabase garde un état de session implicite, pensé pour le navigateur. Réutilisé tel quel côté serveur, cet état devient global à toutes les requêtes, sans aucun avertissement. |
| Pourquoi n'a-t-il pas été détecté plus tôt ? | Les tests simulent le client Supabase et ne font jamais se succéder deux connexions. En recette, un seul compte était actif à la fois : sa session coïncidait avec ses propres données, et RLS laissait passer. Le contrôleur renvoyait le message d'erreur au navigateur sans le journaliser, si bien que Cloud Run ne montrait qu'un statut 500. |
| Qu'est-ce qui empêchera sa récidive ? | Le client partagé ne peut plus conserver de session, un test de non-régression bloque le retour de l'ancien code, et la liste des méthodes proscrites sur ce client est documentée (§ 10). |
